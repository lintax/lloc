# lloc — LLM Localization

Консольная утилита локализации приложений через локальную LLM (Ollama).
Читает базовые строки + контекст из конфигов проекта, переводит только дельту,
валидирует результат и раскладывает по форматам платформ через плагины-адаптеры.

Статус: реализованы M1–M6 (`status`, `translate`, `build`, `verify`, `report`,
`import` включая импорт готовых переводов; адаптеры android-xml, ios, json).
Тесты: `python -m unittest discover -s tests -t .` (161 тест, stdlib unittest).

---

## 1. Принципы

- **Zero-install**: работает на голой стандартной установке Python ≥ 3.11 (Windows/Linux/macOS), без venv и без pip. Только stdlib: `urllib` (HTTP к Ollama), `xml.etree`, `hashlib`, `json`, `tomllib`, `argparse`.
- **Идемпотентность**: повторный запуск ничего не ломает и не делает лишней работы.
- **Только дельта**: переводятся отсутствующие и устаревшие строки; удалённые ключи вычищаются из локалей.
- **Без интерактива**: батчи, можно гонять в фоне; ошибки копятся в отчёт + exit code.
- **Git-friendly**: все состояния — текстовые файлы с детерминированным порядком ключей, коммитятся.
- **Монорепо**: `l10n.toml` может лежать в подкаталоге подпроекта; **все пути в конфиге
  (источники, output) — относительно расположения `l10n.toml`**. Несколько конфигов
  в одном репо = несколько независимых подпроектов, либо один workspace
  (`l10n/config.toml` с `members` в корне репо, §14): запуск из корня
  обрабатывает все модули агрегированно, `--dir <модуль>` — ровно один.

## 2. Формат конфигов: TOML

**Решение: TOML, zero-dependency.** Ключевое наблюдение: файлы делятся на два класса —
человек *пишет*, утилита *читает* (`l10n.toml`, `strings.toml` → tomllib достаточно)
и утилита *пишет*, человек *не правит* (`l10n.lock.json`, `locales/*.json` → JSON).
Read-only ограничение tomllib не мешает вообще. Zero-install сохраняется полностью.
INI (configparser) отпадает из-за плоской структуры и слабых многострочников,
XML — из-за неудобства ручной правки 700+ строк. Слой загрузки изолирован в
`config.py`: смена формата в будущем не затронет остальной код.

## 3. Структура файлов

### 3.1 Репозиторий утилиты (этот каталог)

```
lloc/
├── SPEC.md
├── lloc.py                  # точка входа: python lloc.py <cmd> (обёртка над пакетом)
├── lloc/
│   ├── __init__.py
│   ├── __main__.py          # CLI (argparse, подкоманды), python -m lloc тоже работает
│   ├── config.py            # загрузка/валидация l10n.toml, strings.toml
│   ├── store.py             # locales/*.json + l10n.lock.json, вычисление дельты
│   ├── hashes.py            # канонический хеш базового текста строки
│   ├── ollama.py            # HTTP-клиент Ollama (urllib), structured output
│   ├── prompts.py           # загрузка/рендер промпт-шаблонов, подбор few-shot примеров
│   ├── validate.py          # проверки перевода, генерация текста ошибки для ретрая
│   └── adapters/
│       ├── __init__.py      # реестр адаптеров по имени
│       ├── base.py          # интерфейс Adapter (export / import_ / escape-правила)
│       └── android_xml.py   # первый адаптер
└── prompts/
    ├── translate.txt        # шаблон основного промпта
    └── retry.txt            # шаблон ретрая с текстом ошибки
```

### 3.2 Каталог локализации в проекте-потребителе

Может находиться в любом подкаталоге (мультимодульный проект — по каталогу на модуль):

```
myapp/l10n/                  # или myapp/tv/l10n/, myapp/mobile/l10n/ — независимо
├── l10n.toml            # конфиг проекта (человек)
├── strings.toml         # базовые строки + контекст (человек)
├── l10n.lock.json       # хеши базового текста на момент перевода (утилита, коммитится)
└── locales/             # хранилище переводов (утилита, коммитится)
    ├── ru.json
    ├── de.json
    └── ...
```

Хранилище `locales/` — канонический источник переводов; файлы платформ
(`values/strings.xml` и `values-b+xx/strings.xml`) — генерируемый артефакт
команды `build` (особые ключи в них сохраняются, §8.1).

## 4. Форматы файлов (с примерами)

### 4.1 `l10n.toml`

```toml
[app]
description = """
OTT Navigator — IPTV/медиа-плеер для Android TV и телефонов.
Аудитория: пользователи IPTV-сервисов. UI компактный, много телевизионной терминологии.
"""
tone = "нейтральный, кратко, без канцелярита; обращение на «вы»"
base_language = "en"      # любой язык, английский не обязателен
# BCP-47; порядок = порядок обработки
languages = [
  "ar","az","be","bg","bn","bs","cs","da","de","el","es","es-419","et","fa",
  "fi","fr","hi","hr","hu","id","it","he","ja","jv-Latn","ka","ko","lt","lv",
  "ms","my-Qaag","nl","no","pa","pl","pt","ro","ru","sk","sl","sq","sr",
  "sr-Latn","sv","th","tr","uk","ur","uz","vi","zh",
]

# Опционально, по умолчанию пусто. Ручной глоссарий — это точечный override
# поверх автоматической консистентности терминов (§13): консистентность
# достигается без ручной разметки, сюда вносятся только принудительные решения.
[glossary]
"EPG" = { "*" = "EPG" }       # "*" = не переводить ни на один язык

[ollama]
url = "http://localhost:11434"
model = "gemma4:12b-it-qat"   # см. §6.1
batch_size = 10               # строк в одном запросе
max_retries = 2
timeout_sec = 120
workers = 1                   # параллельных запросов; >1 имеет смысл только при запасе VRAM/RAM

[output]
adapter = "android-xml"

[output.android-xml]
res_dir = "../tv/src/main/res"        # относительно l10n.toml
# BCP-47 -> легаси-код каталога Android (values-b+in, values-b+iw)
legacy_codes = { id = "in", he = "iw" }
```

### 4.2 `strings.toml`

Ключ таблицы = ключ строки. Поля: `text` (обяз.), `context`,
`type` (`button` | `title` | `message`).

```toml
[menu_search]
text = "Search"
context = "Пункт главного меню, ведёт на экран поиска каналов и передач"
type = "button"

[playback_error]
text = "Failed to open stream %1$s. Check your connection."
context = "Сообщение об ошибке при открытии видеопотока; %1$s — имя канала"
type = "message"
```

Норма стиля базовых текстов (не рекомендация): строки с числами формулируются
так, чтобы грамматическая форма не зависела от значения — `"Items: %d"`,
`"People: %d"` вместо `"%d items downloaded"` / `"1 person/5 people"`. Это
снимает проблему плюралей целиком; плюрали не поддерживаются осознанно (§12).
Жёстких лимитов длины per-string нет — есть общая sanity-проверка в
валидации (§7).

Строки, которые в Android помечены `translatable="false"`, в `strings.toml`
просто не заносятся (они остаются только в базовом `values/strings.xml` проекта).

### 4.3 `l10n.lock.json` (пишет утилита, коммитится)

Снимок канонических хешей базового текста. Хеш — `sha256` от
канонизированного представления `text`, усечённый до 16 hex-символов.

```json
{
  "version": 1,
  "keys": {
    "menu_search":    "a1b2c3d4e5f60718",
    "playback_error": "0f1e2d3c4b5a6978",
    "days_count":     "deadbeef00112233"
  }
}
```

### 4.4 `locales/ru.json` (пишет утилита, коммитится)

`src` — хеш базового текста, с которого сделан перевод. Сравнение `src`
с текущим хешем из `strings.toml` и даёт детект устаревших переводов.

```json
{
  "version": 1,
  "language": "ru",
  "strings": {
    "menu_search":    { "text": "Поиск", "src": "a1b2c3d4e5f60718",
                        "model": "gemma4:12b-it-qat", "translated_at": "2026-07-25T12:00:00+00:00" },
    "playback_error": { "text": "Не удалось открыть поток %1$s. Проверьте подключение.", "src": "0f1e2d3c4b5a6978" }
  }
}
```

`model` и `translated_at` — метаданные перевода (кем и когда); у импортированных
записей `model = "imported"`, у ручных исправлений (`set` или прямая правка
locale-файла) — `model = "manual"`. `--force` переписывает всё, включая manual
(force значит force); `--retranslate-model` — честный fnmatch по полю `model`
без спец-кейсов: `gemma*` manual не матчит естественно, явный
`--retranslate-model manual` — матчит. Manual-записи приоритетны при отборе
few-shot примеров, а при изменении базового текста становятся stale и уходят на
пере-перевод с явной пометкой в отчёте translate. Поля опциональны (старые
записи без них валидны); используются командами `report`, `set` и
`translate --retranslate-model`. Все
JSON-хранилища и XML пишутся атомарно (temp + `os.replace`); параллельные
запуски на модуле исключаются OS-локом `.lloc.lock` (flock/msvcrt, умирает
вместе с процессом, ручная чистка не нужна).

Классификация ключа для языка L:
- **missing** — ключа нет в `locales/L.json`;
- **stale** — есть, но `src` ≠ текущий хеш;
- **orphan** — есть в `locales/L.json`, но нет в `strings.toml` → удалить;
- **ok** — иначе.

Роль lock-файла: зафиксированный снимок «что считалось базой» — по диффу
lock в PR видно, какие исходные строки изменились и потянут перевод; также
`verify` сверяет lock с фактическими `src` в локалях (консистентность репо).

## 5. CLI

```
python lloc.py <command> [options]        # или python -m lloc
```

Общие опции: `--dir PATH` (каталог с l10n.toml или корень workspace c
l10n/config.toml, §14; по умолчанию `.`), `--lang xx[,yy]` (ограничить языки),
`--verbose`.

| Команда | Действие |
|---|---|
| `status` | Таблица по языкам: ok / missing / stale / orphan / failed. Ничего не меняет. Exit code 0 если всё ok, 1 если есть работа. |
| `translate` | Перевод дельты: missing + stale, чистка orphan, обновление locales/ и lock, затем автоматически `build`. Опции: `--force` (перевести всё заново для указанных `--lang`), `--limit N`, `--dry-run` (показать план без запросов к LLM), `--no-build`. |
| `build` | Сгенерировать файлы платформы из `locales/` через адаптер. Без обращений к LLM. |
| `import` | Миграция: прочитать существующие переводы адаптером (values-b+xx) в `locales/`, `src` = текущий хеш базы (считаем актуальными). Опции: `--assume-stale` (пометить импортированное устаревшим), `--overwrite` (перезаписать существующие записи в locales/). |
| `verify` | Прогнать валидации над уже существующими переводами + проверить консистентность lock/locales. Без LLM. Exit code ≠ 0 при провалах. |
| `report` | Ревью свежепереведённого по `translated_at` (`--since 90m/24h/7d`, default 24h). Без LLM. |
| `set` | Ручное исправление: `set <key> --lang xx "текст"` → запись в locales с `model="manual"` (приоритетный few-shot пример; модельные паттерны `--retranslate-model` её не матчат, `--force` переписывает всё) + инкрементальный build языка. Валидация как у translate, `--force-set` — override. |

### Поток данных `translate`

```
strings.toml ──hash──┐
                     ├─► дельта (missing/stale) ─► батчи ─► промпт ─► Ollama
locales/*.json ──────┘                                        (format: json schema)
                                                                  │
        ┌──────────── ретрай с текстом ошибки (≤ max_retries) ◄── валидация
        │                                                         │ ok
        ▼ fail                                                    ▼
   отчёт + failed                                        locales/*.json (запись
                                                         после каждого батча)
                                                                  │
                                                     lock update ─┴─► build ─► адаптер
                                                                       (values-b+xx/strings.xml)
```

Запись после каждого батча ⇒ прерванный запуск не теряет работу; повторный
запуск продолжает с оставшейся дельты (идемпотентность).

## 6. Перевод через Ollama

- `POST {url}/api/chat`, `stream: false`, `format:` = JSON-схема ответа
  (structured output). Схема генерируется по батчу: `{key: string}` для каждой
  строки батча, все ключи required.
- `"think": false` — думающие модели (qwen3.5, deepseek-r1) иначе кладут ответ в
  `message.thinking`, оставляя `content` пустым. Если модель не понимает параметр,
  клиент автоматически повторяет запрос без него и больше его не шлёт.
- `options.num_ctx` — явно (default 8192, `[ollama] num_ctx` в l10n.toml):
  дефолт Ollama 4096 может резать промпт с примерами.
- Пустой/невалидный JSON в ответе — **не фатальная ошибка, а обычный ретрай**
  (как провал валидации): до `max_retries` повторов, затем ключи батча помечаются
  failed, обработка продолжается. Фатальны только транспортные ошибки
  (Ollama недоступна). Известная особенность: Ollama иногда
  не enforce'ит схему на новых моделях ([issue #15540](https://github.com/ollama/ollama/issues/15540)) —
  наш парсер ответа не доверяет схеме и валидирует всё сам (§7); низкая
  температура (0–0.2) повышает соблюдение схемы.
- **Авто-загрузка модели**: HTTP API (в отличие от `ollama run`) не скачивает
  модель сам — на отсутствующую модель приходит 404 «model not found». Клиент
  детектит это, вызывает `/api/pull` (stream, прогресс скачивания в консоли,
  глобальный lock — одна загрузка даже при `workers > 1`) и повторяет запрос.
  Если pull не удался (модель не существует / нет сети) — понятная ошибка с
  подсказкой `ollama pull <model>`.
- `workers` (конфиг, default 1) — число параллельных запросов к Ollama
  (например, разные языки одновременно). Выгодно только при достаточном
  VRAM/RAM; на одной нагруженной GPU оставлять 1.
- Структура промпта (порядок важен):
  1. глобальный контекст приложения (`app.description`, `tone`, глоссарий для
     целевого языка — если задан);
  2. целевой язык + правила (сохранять плейсхолдеры и т.п.);
  3. для каждой строки: ключ, базовый текст, `context`, `type`;
  4. few-shot: уже переведённые на этот язык строки с похожими терминами
     (отбор по авто-извлечённым терминам, §13, затем по пересечению слов),
     с явной инструкцией: **контекст строки важнее похожести написания** —
     одинаковые слова в разных контекстах могут переводиться по-разному.
- Шаблоны промптов — в `prompts/*.txt`, плейсхолдеры `{app_context}`,
  `{target_language}`, `{strings_block}`, `{examples_block}`, `{error}`.
  Меняются без правки кода; путь переопределяется в `l10n.toml`
  (`[ollama] prompts_dir = ...`).

### 6.1 Выбор модели (состояние на июль 2026)

Модель настраивается (`[ollama] model` или `translate --model` для A/B);
дефолт для NVIDIA 12 ГБ VRAM:

| Модель | Размер | Итог A/B на examples/demo (12 строк × ru/de/ja/ar) |
|---|---|---|
| **`gemma4:12b-it-qat`** (default) | 7.2 GB, 256K ctx | победитель 3 из 4 языков: ru — «Прямой эфир» против ошибочного «Эфирное TV», ar — верное родовое согласование, ja — естественнее; батчи 1.3–2.5с |
| `qwen3.5:9b` | 6.6 GB, 256K ctx | чуть быстрее (0.9–1.7с/батч), 201 язык; проиграл на коротких кнопочных строках и грамматике ar; выдержаннее регистр в de |
| `gemma3:12b` | ~8 GB | прежний baseline, устарел |

`qwen3.5:27b` (17 GB) и `gemma4:26b` (16–18 GB) в 12 ГБ не помещаются.
Разница размеров дефолта и альтернативы (0.6 GB) непринципиальна; при
`workers > 1` Ollama не дублирует веса (растёт только KV-cache), так что обе
модели пригодны для параллели. Плейсхолдеры обе модели сохраняют надёжно.

## 7. Валидация (`validate.py`)

Для каждого переведённого значения:

1. **Плейсхолдеры**: мультимножество `%s`, `%d`, `%1$s`…, `\n` совпадает с базой.
2. **Длина**: sanity-проверка — отношение длины к базе ≤ `length_ratio`
   (конфиг, по умолчанию 3.0; для CJK порог мягче не нужен — они короче).
3. **Чистота**: ответ не содержит рассуждений/кавычек-обрамления/пустых значений
   (эвристики).

**Не ошибка**: перевод, дословно совпадающий с оригиналом. В близких языках
(en/de/nl/sv…) и для терминов множество строк совпадают легитимно
("Start", "Status", "OK") — совпадение не признак неудачи и не триггерит ретрай.

Экранирование под целевой формат (`\'`, `&amp;`…) — зона ответственности
адаптера при `build`, в `locales/` текст хранится сырым. Поэтому валидация
формата (например, что после экранирования XML валиден) выполняется адаптером
на этапе `build` и в `verify`.

Провал → ретрай с шаблоном `retry.txt`: диалог продолжается (исходный промпт →
ответ модели → сообщение с конкретными ошибками), JSON-схема сужается до
провалившихся ключей. После `max_retries` — строка помечается `failed` в отчёте,
остальные продолжают обрабатываться.

Нюанс реализации: для коротких строк порог длины считается от
`max(len(base), 10)`, иначе «OK» → «Хорошо» (3×) давал бы ложный провал.

## 8. Адаптеры (`adapters/`)

Интерфейс (`base.py`):

```python
class Adapter:
    name: str
    def export(self, project, locales) -> None: ...   # locales/ -> файлы платформы
    def import_(self, project) -> dict: ...           # файлы платформы -> {lang: {key: value}}
    def check(self, text, base) -> list[str]: ...     # форматные проверки для verify
```

Регистрация по имени в `adapters/__init__.py`; `[output] adapter = "..."` выбирает.

### 8.1 `android-xml` (первый)

- Каталоги `values-b+xx` (BCP-47 c `+` вместо `-`), легаси-коды из
  `legacy_codes` (id→in, he→iw); скрипты/регионы: `es-419` → `values-b+es+419`,
  `sr-Latn` → `values-b+sr+Latn`.
- Запись: UTF-8, **без XML-декларации** (как в текущем проекте), отступ 4 пробела,
  порядок ключей = порядок в `strings.toml`; непереведённые ключи пропускаются.
- Экранирование: `\'`, `\"`, `\\`, `\n`, `\t`, `&` → `&amp;`, `<` → `&lt;`,
  `>` → `&gt;`; ведущие `@`/`?` экранируются (ссылки на ресурсы).
- Дефолтный `values/` (базовый язык) участвует наравне с `values-b+xx`:
  `build` генерирует и `values/strings.xml` (базовые тексты из `strings.toml`),
  `import --bootstrap-strings` читает его как раньше.
- **Особые ключи — «пропускать и не трогать»**. Управляемые записи — только
  обычные переводимые `<string>`; всё остальное (`translatable="false"`,
  `<string-array>`, `<plurals>`, прочие не-string ресурсы) в `strings.toml`
  при импорте не попадает, а при `build` сохраняется: файл переписывается
  целиком (managed-строки перегенерируются, посторонние plain-строки
  выпадают), особые блоки существующего файла дописываются без изменений —
  в исходном порядке, вместе с комментариями (парсинг через
  `TreeBuilder(insert_comments=True)`, иначе `xml.etree` их теряет; комментарий
  непосредственно перед особым блоком считается его частью, комментарии перед
  managed-строками относятся к перегенерируемому содержимому и отбрасываются).
  Действует и для `values/`, и для локалей.
- `import`: парсит существующие `strings.xml`, деэкранирует,
  пропускает ключи, отсутствующие в `strings.toml`, и особые ключи.

### 8.2 `ios` и `json` (реализованы, M6)

Три адаптера, все чисто на stdlib — новых зависимостей нет:

| Адаптер | Формат | stdlib-инструменты |
|---|---|---|
| `android-xml` (M2) | `values-b+xx/strings.xml` | `xml.etree` |
| `ios` (M6) | `<код>.lproj/Localizable.strings` («"key" = "value";», UTF-8) | ручной parser/writer (`ios_strings.py`) |
| `json` (M6) | плоский `<код>.json` на язык, i18next-совместимый | `json` |

Общая дисциплина всех адаптеров: управляемые ключи (те, что в `strings.toml`)
перегенерируются при `build`; всё постороннее в существующих файлах
сохраняется («skip and keep», как в §8.1); запись атомарная; `import_` читает
существующие переводы; `bootstrap_source` — базовый файл.

`ios`: каталоги `<BCP-47>.lproj` как есть (`es-419.lproj`, `pt-BR.lproj`,
`zh-Hant.lproj`); базовый язык — `<base>.lproj` (язык разработки; `Base.lproj`
не используется — это механизм сторибордов, не строк); `context` строки
пишется комментарием `/* ... */` над записью, комментарий над неуправляемой
парой сохраняется вместе с ней; экранирование `\" \\ \n \t \r`; плейсхолдеры
`%@`/`%1$@` включены в PLACEHOLDER_RE (§7); `check` — roundtrip
serialize/parse. `.stringsdict` не трогается (§12).

`json`: плоский объект, ключи сортированы, `ensure_ascii=False`; точки в
ключах литеральные (без вложенности); непереведённые ключи опускаются;
неуправляемые ключи существующего файла сохраняются.

Легаси-коды Android (`in`/`iw`) в именах файлов ios/json не используются —
конвертация в `id`/`he` через `langnames.canonical_code`.

`locales/` формат-независим, так что добавление адаптера не трогает ядро.
Прочее (`po`/gettext и т.д.) — возможно позже по той же схеме.

## 9. Миграция ottnavigator (первый прогон)

1. Один раз сгенерировать `strings.toml` из базового `values/strings.xml`
   (вспомогательный скрипт/режим `import --bootstrap-strings`): текст берётся
   как есть, `context`/`type` заполняются позже вручную по мере надобности.
2. `python lloc.py import` — 46 языков × 737 строк уезжают в `locales/` без LLM.
3. `python lloc.py status` — видно реальную дельту (ожидаемо близкую к нулю).
4. Дальше обычный цикл: правка `strings.toml` → `translate`.
5. Пере-перевод выбранных языков: `translate --force --lang xx,yy`.

## 12. Плюрали — отвергнуты дизайном

Позиция: **плюрали не поддерживаются, это осознанное дизайн-решение, а не
отложенная фича**. Каноничный подход утилиты — числонезависимые базовые
тексты: `"People: %d"`, а не `"1 person/5 people"`. Это норма стиля (§4.2),
а не обходной манёвр: она проще для перевода на 60+ языков, устойчивее к
CLDR-категориям (у русского их четыре, у арабского шесть) и снимает целый
класс ошибок LLM-перевода. В ottnavigator `<plurals>` не используются вовсе
(проверено).

Практические следствия:

- plural-таблица в `strings.toml` (`[key.text]` с формами) — ошибка загрузки
  с внятной подсказкой («plurals are not supported by design, rephrase as
  "Items: %d"») — остаётся навсегда, это не заглушка до реализации;
- особые конструкции платформ (`<plurals>` в Android, `.stringsdict` в iOS)
  утилитой не управляются: android-адаптер сохраняет `<plurals>` в XML
  нетронутыми (§8.1), ios-адаптер не трогает `.stringsdict`-файлы, у
  json-адаптера суффиксные ключи i18next (`_one`/`_other`) — обычные
  неуправляемые ключи, переживающие `build`;
- рантайм-форматирование чисел/дат — зона ICU/платформы, не `strings.toml`.

## 13. Автоматическая консистентность терминов (реализовано, `terms.py`)

Ручной глоссарий на 40–50 языков поддерживать никто не будет. Консистентность
должна получаться автоматически; `[glossary]` остаётся опциональным точечным
override (его записи для языка подставляются в промпт как обязательные и
выигрывают у автомеханизма).

### 13.1 Извлечение терминов (без разметки, без LLM)

Кандидат в термины — слово или биграмма базового языка, встречающаяся в
**разных** строках `strings.toml` не менее `min_occurrences` раз (default 3;
биграммы — 2). Вычисляется на лету при каждом запуске, ничего не хранится.
Фильтрация служебных слов не по ручному списку (база может быть любым языком),
а по document frequency: слово, встречающееся более чем в `stopword_df`
(default 35%) строк — служебное («the», «to»…) и термином не считается;
для маленьких наборов строк DF дополнен абсолютным порогом (стоп-слово —
не менее чем в 5 строках), слова короче 3 символов кандидатами не являются.
Сравнение слов: casefold + общий префикс ≥ 4 символов (дёшево гасит
морфологию: channel/channels, канал/канала). Настройки — секция `[terms]`
в l10n.toml, все дефолты рабочие без конфигурации.

### 13.2 Использование при переводе (мягкое, через few-shot)

Ключевая проблема: без пословного выравнивания мы **не знаем**, как термин
переведён внутри принятой строки. Поэтому никаких словарей «термин → перевод»
автоматика не строит. Вместо этого отбор few-shot примеров (§6) приоритизирует
принятые строки, разделяющие с батчем именно *термины* (а не любые слова),
и группирует их в промпте под инструкцией вида: «these approved translations
contain the same terms; keep terminology consistent with them **unless the
string's context requires otherwise**». Выравнивание делает сама модель.
Enforce нет: валидация (§7) консистентность не проверяет и ретраев не вызывает.

### 13.3 Детект расхождений в `verify` (двухуровневый)

- **Дёшево, без LLM (default)**: для каждого термина берём принятые переводы
  всех строк с ним; если у подмножества переводов нет ни одного общего слова
  (по префикс-совпадению ≥ 4), термин помечается «возможное расхождение» —
  **warning, не ошибка** (exit code не трогает). Работает только для языков с
  пробельной сегментацией; ja/zh/th героически не анализируем эвристикой.
- **Точно, с LLM (`verify --terms`)**: моделью строится терм-карта языка —
  батч-запросы «каким словом в этом переводе выражен термин X» (structured
  output). Карта кешируется в `terms/<lang>.json` (пишет утилита, коммитится)
  с src-хешами — повторный `verify --terms` переспрашивает только изменившееся;
  orphan-чистка кеша (удалённые строки/термины) выполняется офлайн при каждом
  `translate`, LLM для этого не нужна.
  Расхождение = термин имеет ≥ 2 вариантов перевода; в отчёте — варианты,
  ключи строк и majority-вариант.

Сравнение вариантов **морфологически толерантно на целевой стороне** (иначе
склонения дают ложные срабатывания): пословно, общий префикс ≥ max(3, len−2)
(«этот канал» ~ «этого канала», Sender ~ Sendern; но канал ≁ телеканал,
Kanäle ≁ Sender); при разном числе слов — каждое слово короткого варианта
должно найтись в длинном («канала» ~ «этот канал»); для арабского — сравнение
консонантных скелетов со срезанием артикля ال (القناة ~ قنوات); для
несегментированных письменностей (ja/zh…) — вхождение подстроки
(ロック ~ ロックされています). Ответ «-» (термин опущен в переводе) вариантом
не считается.

### 13.4 Авто-исправление (`translate --fix-terms`)

Для строк из меньшинства: пере-перевод с промптом, где примеры
majority-варианта закреплены явно («in this app, X is translated as ... — use
it unless this string's context demands otherwise»). Именно пере-перевод с
контекстом, а не текстовая замена: если модель **снова** выбирает иной вариант,
расхождение считается осмысленным (полисемия: «Play» кнопка ≠ «play» пьеса),
фиксируется в `terms/<lang>.json` как accepted и больше не флагуется
(идемпотентность). Majority считается только по строкам в статусе ok; при
слабом большинстве (< 60%) вместо голосования модель просят выбрать лучший
вариант по совокупности контекстов.

### 13.5 Подводные камни (учтены в дизайне)

- **Легитимная полисемия** → только мягкий enforce; accepted-расхождения
  запоминаются, а контекст в промпте всегда важнее консистентности.
- **Ранний плохой выбор распространяется** через few-shot (первая переведённая
  строка задаёт термин остальным). Смягчение: majority по ok-строкам,
  `--fix-terms` пересматривает меньшинство, слабое большинство отдаётся на
  решение модели, ручной глоссарий — последнее слово.
- **Морфология и сегментация**: префикс-эвристика не работает для ja/zh/th и
  слаба для ar — для них только LLM-уровень (13.3b).
- **Словообразование ≠ словоизменение** (подтверждено вживую): извлечение
  склеило play + player, из-за чего `--fix-terms` пере-перевёл слоган с
  «плеером» под закреплённое «воспроизвести» и потерял понятие. Надёжного
  лексического критерия различения нет; лечится правкой пострадавшей строки в
  `locales/` (канонический источник) или глоссарным override. Override
  реализован в экстракции: слово из `[glossary]` — всегда самостоятельный
  термин и граница префикс-слияния (player не поглощается play, в `text_terms`
  такое слово матчит только себя), при этом склонения по-прежнему сливаются
  (players → player, channels → channel).
- **Стоимость**: экстракция и эвристика — бесплатны; LLM-терм-карта — по
  явному запросу и инкрементально по src-хешам.

## 14. Workspace-режим для монорепо (реализовано)

### 14.1 Структура и дискавери

Всё workspace-уровневое живёт в **одном каталоге `l10n/` в корне монорепо**,
никаких других файлов/каталогов утилита в корень не добавляет:

```
monorepo/
├── l10n/
│   ├── config.toml      # корневой конфиг: members + workspace-дефолты
│   └── player.toml      # группа "player": любой *.toml кроме config.toml —
│                        #   группа, имя файла = тег
├── apps/tv/l10n.toml    # модульные конфиги — в каталогах модулей, как обычно
├── apps/mobile/l10n.toml
└── libs/core/l10n.toml
```

Workspace-режим включается наличием `l10n/config.toml` с `members` —
**явные глобы, без автосканирования** (`members = ["apps/*", "libs/*"]`,
относительно корня; матчи без `l10n.toml` игнорируются, глоб без единого
модуля — ошибка). Одиночный режим (`l10n.toml` рядом со `strings.toml`)
не изменён. Вложенные workspace запрещены: member с `members` — ошибка;
`members` в модульном `l10n.toml` — ошибка.

### 14.2 Наследование (строго два уровня)

Workspace-дефолты (`[app]` языки/тон/базовый язык, `[ollama]`, `[terms]`,
`[validation]`, `[glossary]`) → модульный `l10n.toml` (описание модуля,
`[output]`/адаптер/пути; может переопределять любые унаследованные ключи
поверх, per-key). `description` не наследуется никогда — оно модульное.

### 14.3 Группы-теги

Определение группы — файл `l10n/<tag>.toml` с полем `context` (описание
продукта; редактируется командой продукта, корневой конфиг остаётся тонким).
Модуль указывает `group = "player"` (top-level или в `[app]`); группа без
файла — ошибка (ловит опечатки). Модуль без `group` — сам себе группа
(файл не нужен).

Слоёная сборка контекста промпта: тон workspace → `context` группы →
`description` модуля (короткая специфика, например «сборка под Amazon») →
`context` строки.

### 14.4 Границы группы

Группа — граница консистентности:

- **few-shot**: кандидатами становятся и принятые переводы модулей-соседей
  по группе (другие группы не видны никогда);
- **термины**: частоты/стоп-слова экстракции считаются по корпусу всей
  группы (термин может «добраться» до `min_occurrences` строками соседа),
  списки ключей термина остаются модульными — терм-карты, `verify --terms`
  и `--fix-terms` работают per-модуль над его locale;
- **дубликаты ключей**: `verify` предупреждает о совпадающих ключах между
  модулями одной группы (Android мержит ресурсы молча) — warning, exit code
  не трогает.

### 14.5 Запуск

Из корня: `status`/`translate`/`build`/`verify` обходят все members
агрегированно, в выводе префикс модуля (`[apps/tv:ru] ...`); `translate`
использует **один общий пул воркеров на весь прогон** (`workers` из
дефолтов workspace). `import` в workspace-режиме — только per-модуль
(`--dir <member>`). `--dir <модуль>` ограничивает запуск одним модулем,
при этом наследование/группа/соседи подхватываются автоматически (поиск
`l10n/config.toml` вверх по дереву). Lock и `locales/` — per-модуль,
как раньше. Обкатка: `examples/demo-workspace` (2 приложения + общая
библиотека, группа "player").
